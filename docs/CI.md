# Сборка и установка на телефон

Два workflow в `.github/workflows`:

| Файл | Когда срабатывает | Что даёт |
|---|---|---|
| `build.yml` | пуш в любую ветку, кроме правок только в `docs/` и `*.md` | проверяет, что проект компилируется, и кладёт Debug-APK в артефакты запуска |
| `release.yml` | кнопка **Run workflow** с тегом | собирает подписанный APK, создаёт тег и публикует релиз |
| `release.yml` | кнопка **Run workflow** без тега | репетиция: APK собирается и подписывается, Releases не трогается |
| `release.yml` | пуш тега `v*` | то же, что первое, но из командной строки |

## Получить установочный файл

**Релиз.** Вкладка **Actions** → **Release APK** → **Run workflow** → в поле тега ввести
`v1.0.0` → запустить. Тег создастся сам на текущем коммите, а через несколько минут APK
появится в разделе **Releases**.

Оставьте поле пустым, если нужно просто прогнать сборку: APK соберётся и подпишется, но
останется артефактом запуска — удобно проверить пайплайн или ключ, не оставляя мусора
в списке релизов.

Из командной строки то же самое делается пушем тега:

```bash
git tag v1.0.0
git push origin v1.0.0
```

> Кнопка **Run workflow** появляется, только когда `release.yml` есть в ветке по умолчанию:
> GitHub ищет workflow с триггером `workflow_dispatch` именно там. Пока ветка с ним не
> слита в `main`, доступен только путь через пуш тега.

**Без релиза.** Вкладка **Actions** → последний запуск **Build** → блок **Artifacts**
внизу страницы. Скачивается zip, внутри APK. Этот путь удобен, чтобы быстро проверить
свежий коммит.

## Установить на Android

1. Скачайте `.apk` на телефон (прямо из браузера в Releases).
2. Откройте файл. Android спросит разрешение на установку из этого источника — разрешите
   его для браузера или файлового менеджера, из которого открываете.
3. Дальше обычная установка.

Приложению не нужны ни аккаунт, ни интернет: база лежит на устройстве.

## Ключ подписи

Android ставит обновление поверх старой версии, только если обе подписаны **одним и тем же**
ключом. Пока постоянный ключ не настроен, каждая сборка подписывается одноразовым, и при
установке новой версии поверх прежней система откажет — придётся удалить старую вместе с
данными. Workflow предупреждает об этом прямо в описании релиза.

Настроить постоянный ключ — один раз:

```bash
keytool -genkeypair -v \
  -keystore medical-results.keystore \
  -alias medical-results \
  -keyalg RSA -keysize 2048 -validity 10000

base64 -w0 medical-results.keystore > keystore.base64   # macOS: base64 -i ... -o ...
```

В репозитории: **Settings → Secrets and variables → Actions → New repository secret**,
четыре секрета:

| Секрет | Значение |
|---|---|
| `ANDROID_KEYSTORE_BASE64` | содержимое `keystore.base64` |
| `ANDROID_KEYSTORE_PASSWORD` | пароль хранилища |
| `ANDROID_KEY_ALIAS` | `medical-results` |
| `ANDROID_KEY_PASSWORD` | пароль ключа (обычно тот же) |

Файл `medical-results.keystore` храните вне репозитория и не теряйте: без него обновления
поверх установленной версии станут невозможны навсегда.

## Что стоит знать

- Сборка идёт на `ubuntu-latest`, поэтому собирается только Android — iOS требует macOS-раннера
  и сертификатов Apple.
- Релиз создаётся через `gh` — GitHub CLI предустановлен на раннере, сторонние экшены для
  публикации не нужны.
- `build.yml` не собирает pull request'ы: тот же коммит уже собрался по пушу, и второй запуск
  был бы одинаковой работой дважды одновременно. Новый пуш в ветку отменяет предыдущую сборку
  (`concurrency`), релизы, наоборот, ждут друг друга — прерывать публикацию на полпути нельзя.

## Тег — единственный источник версии

Версия сборки не задаётся нигде, кроме тега релиза. Значения в `.csproj` (`1.0`, `1`)
на релиз не влияют: их перекрывает workflow.

| Что | Откуда берётся | Пример для `v1.2.3` |
|---|---|---|
| `ApplicationDisplayVersion` — версия в списке приложений | тег без `v` | `1.2.3` |
| `ApplicationVersion` — versionCode для Android | арифметика по тегу: `major·1000000 + minor·1000 + patch` | `1002003` |

versionCode считается **из тега**, а не из номера запуска CI. Иначе пересборка того же тега
дала бы APK с другим внутренним номером, и тег перестал бы однозначно означать сборку.
Ограничение схемы: `minor` и `patch` должны быть меньше 1000.

Второй замок — шаг **Check tag is free**: если тег уже стоит на другом коммите, запуск падает
с ошибкой вместо того, чтобы молча перезаписать релиз. Под одним номером версии не может
оказаться разный код. Повторный запуск на том же коммите разрешён — он просто обновит файл.

Проверить, что установлено на телефоне, можно в **Настройках**: там показаны версия и номер
сборки (`AppInfo.Current`). Они должны совпадать с тегом релиза, из которого поставлен APK.
